## 1. วัตถุประสงค์เอกสาร
เอกสารนี้กำหนดข้อกำหนดเชิงผลิตภัณฑ์ของระบบยืม-คืนหุ่น/อุปกรณ์ เพื่อให้ทีมที่เกี่ยวข้อง (Product, UX/UI, Dev, QA, Admin) ใช้เป็นมาตรฐานเดียวกันในการพัฒนา ทดสอบ และส่งมอบระบบ

## 2. ภาพรวมผลิตภัณฑ์
ระบบยืม-คืนหุ่น/อุปกรณ์ SIMSET เป็นระบบเว็บสำหรับ:
- ผู้ยืม: ค้นหาอุปกรณ์ เลือกช่วงวันยืม-คืน ส่งคำขอ ติดตามสถานะ
- เจ้าหน้าที่: ตรวจสอบคำขอ อนุมัติ/ไม่อนุมัติ บันทึกคืน ตรวจสภาพ และติดตามประวัติ
- ผู้ดูแลระบบ: บริหารข้อมูลอุปกรณ์ สิทธิ์ผู้ใช้งาน และรายงานการใช้งาน

## 3. เป้าหมายและขอบเขต
### 3.1 Product Goals
- ลดเวลาการทำรายการยืม-คืนจากกระบวนการแมนนวล
- ลดการจองทับซ้อนและข้อผิดพลาดด้านสต็อก
- ทำให้ตรวจสอบสถานะคำขอได้แบบโปร่งใสและตรวจสอบย้อนหลังได้
- รองรับการปฏิบัติงานจริงของหน่วยงาน (ยืม-คืนบางส่วน, ของชำรุด, รอซ่อม)

### 3.2 Out of Scope (Version นี้)
- ระบบชำระเงินออนไลน์
- Mobile Native App
- การเชื่อม ERP เต็มรูปแบบ

## 4. ผู้ใช้งานและบทบาท
- Borrower (ผู้ยืม): สร้างคำขอยืม ติดตามสถานะ ยกเลิกก่อนอนุมัติ
- Staff/Admin (เจ้าหน้าที่): พิจารณาคำขอ จัดการคืน บันทึกผลการตรวจสภาพ
- System Admin (ผู้ดูแลระบบ): จัดการข้อมูลหลัก สิทธิ์ผู้ใช้ ค่าระบบ และรายงาน

## 5. ขอบเขตฟังก์ชันหลัก
- Catalog และการค้นหาอุปกรณ์
- เลือกช่วงวันที่ยืม-คืนและตรวจสอบความพร้อมใช้งาน
- สร้างคำขอยืมและยืนยันข้อมูล
- Workflow อนุมัติ/ไม่อนุมัติ
- ติดตามสถานะคำขอด้วยเลขอ้างอิง
- รับคืน/คืนบางส่วน/บันทึกชำรุด/ส่งซ่อม
- Dashboard และรายงานเชิงปฏิบัติการ
- Audit Log และการตรวจสอบย้อนหลัง

## 6. Workflow มาตรฐานระบบยืม-คืน
1. ผู้ใช้เข้าสู่ระบบ
2. เลือกช่วงวันยืมและวันคืน
3. ระบบคำนวณจำนวนคงเหลือในช่วงวันที่เลือก
4. ผู้ใช้เลือกอุปกรณ์และจำนวน แล้วส่งคำขอ
5. ระบบสร้างคำขอด้วยสถานะ `pending`
6. เจ้าหน้าที่ตรวจสอบและอนุมัติ (`approved`) หรือปฏิเสธ (`rejected`)
7. เมื่อคืนอุปกรณ์ เจ้าหน้าที่บันทึกผลคืน:
   - คืนสมบูรณ์ (`returned`)
   - คืนบางส่วน/รอตรวจ (`returned_pending_inspection`)
   - มีชำรุด/ส่งซ่อม (ระดับรายการ)
8. ระบบอัปเดตสต็อกและประวัติการใช้งานอัตโนมัติ

## 7. Functional Requirements (FR)
### 7.1 Borrower
- FR-01: ผู้ยืมต้องเลือกวันที่ยืมและวันที่คืนก่อนเพิ่มรายการ
- FR-02: ระบบต้องแสดงจำนวนพร้อมใช้งานตามช่วงวันจริง (กันจองทับซ้อน)
- FR-03: ผู้ยืมเพิ่มรายการหลายชนิดในคำขอเดียวได้
- FR-04: ผู้ยืมส่งคำขอแล้วได้รับเลขติดตาม
- FR-05: ผู้ยืมตรวจสอบสถานะคำขอได้จากหน้า Tracking
- FR-06: ผู้ยืมยกเลิกคำขอได้เฉพาะสถานะ `pending`

### 7.2 Staff/Admin
- FR-07: เจ้าหน้าที่เห็นรายการคำขอแยกตามสถานะ
- FR-08: เจ้าหน้าที่อนุมัติ/ไม่อนุมัติพร้อมบันทึกเหตุผลได้
- FR-09: เจ้าหน้าที่บันทึกการคืนแบบเต็มหรือบางส่วนได้
- FR-10: เจ้าหน้าที่บันทึกรายการชำรุดและส่งซ่อมระดับรายการได้
- FR-11: ระบบต้องเก็บ Audit Log การเปลี่ยนสถานะทุกครั้ง

### 7.3 Data & Document
- FR-12: ระบบต้องสร้างเลขเอกสาร/เลขอ้างอิงไม่ซ้ำ
- FR-13: ระบบต้องเก็บประวัติการแก้ไขเอกสารแบบมี revision
- FR-14: ระบบต้องผูกคำขอหลักกับรายการย่อย (Header/Item) อย่างถูกต้อง

## 8. กติกาธุรกิจ (Business Rules)
- BR-01: วันยืมต้องน้อยกว่าหรือเท่ากับวันคืน
- BR-02: ห้ามสร้างคำขอถ้าจำนวนที่ต้องการมากกว่าจำนวนว่างในช่วงวันนั้น
- BR-03: การชนกันของวันให้ใช้กติกา Inclusive Date (วันซ้ำถือว่าชน)
- BR-04: คำขอ `pending` ที่เกินเวลาที่กำหนดสามารถหมดอายุ (`expired`) ได้
- BR-05: เฉพาะเจ้าหน้าที่ที่มีสิทธิ์เท่านั้นที่เปลี่ยนสถานะคำขอได้
- BR-06: การคืนบางส่วนต้องไม่ทำให้ยอดคืนรวมเกินยอดยืม

## 9. ข้อกำหนดข้อมูล (Data Requirements)
### 9.1 เอนทิตีหลัก
- Equipment
- Equipment Unit (กรณีติด Serial)
- Borrow Request (Header)
- Borrow Request Item (Detail)
- Document Artifact
- Notification Log
- Audit Log

### 9.2 ข้อมูลขั้นต่ำที่ต้องจัดเก็บ
- ข้อมูลผู้ยืม: ชื่อ, อีเมลหน่วยงาน, หน่วยงาน, เบอร์ติดต่อ
- ข้อมูลคำขอ: วันที่ยืม, วันที่คืน, เหตุผลการใช้งาน, สถานะ
- ข้อมูลรายการ: รหัสอุปกรณ์, จำนวนยืม, จำนวนคืนปกติ/ชำรุด/ซ่อม
- ข้อมูลตรวจสอบย้อนหลัง: ผู้แก้ไข, เวลา, เหตุผล, สถานะก่อน-หลัง

## 10. Non-Functional Requirements (NFR)
- NFR-01 Availability: ระบบพร้อมใช้งานอย่างน้อย 99.5% ต่อเดือน
- NFR-02 Performance: หน้าใช้งานหลักควรตอบสนองภายใน 2 วินาที (P95) ภายใต้โหลดปกติ
- NFR-03 Security: บังคับ Authentication/Authorization ตามบทบาท
- NFR-04 Privacy: ปกป้องข้อมูลส่วนบุคคลตามนโยบายองค์กร
- NFR-05 Auditability: ตรวจสอบประวัติการเปลี่ยนแปลงย้อนหลังได้ครบ
- NFR-06 Reliability: ธุรกรรมสำคัญ (อนุมัติ/คืน/ปรับสถานะ) ต้องไม่เกิดข้อมูลไม่สอดคล้อง

## 11. Security & Compliance
- Role-Based Access Control (RBAC): Borrower, Staff/Admin, System Admin
- บันทึก Log การเข้าใช้งานและการเปลี่ยนสถานะสำคัญ
- ใช้ HTTPS ทุกสภาพแวดล้อม
- ซ่อน/Mask ข้อมูลส่วนบุคคลในหน้าสาธารณะ
- ควบคุมสิทธิ์การเข้าถึงข้อมูลตามหลัก Least Privilege

## 12. รายงานและตัวชี้วัด (KPI)
- จำนวนคำขอรายวัน/รายเดือน
- อัตราอนุมัติ/ปฏิเสธ
- ระยะเวลาจากสร้างคำขอถึงอนุมัติ (Lead Time)
- อัตราการคืนตรงเวลา
- อัตราของชำรุด/ส่งซ่อม
- Top อุปกรณ์ที่ถูกใช้งานสูงสุด

## 13. เกณฑ์การยอมรับระบบ (UAT Acceptance Criteria)
- AC-01: ผู้ยืมสามารถสร้างคำขอจากต้นทางถึงได้เลขติดตามสำเร็จ
- AC-02: ระบบป้องกันการจองเกินจำนวนและจองทับซ้อนได้จริง
- AC-03: เจ้าหน้าที่อนุมัติ/ปฏิเสธและเปลี่ยนสถานะได้ตามสิทธิ์
- AC-04: รองรับคืนเต็ม/คืนบางส่วนพร้อมบันทึกผลชำรุดได้
- AC-05: ประวัติการเปลี่ยนสถานะย้อนหลังตรวจสอบได้ครบ
- AC-06: หน้าติดตามแสดงสถานะปัจจุบันถูกต้องกับฐานข้อมูล

## 14. ข้อจำกัดและความเสี่ยง
- ความครบถ้วนของข้อมูลตั้งต้นอุปกรณ์และจำนวนคงเหลือ
- ความถูกต้องของสิทธิ์ผู้ใช้งานในแต่ละบทบาท
- ความเสี่ยงจากข้อมูลวันที่ผิดรูปแบบ/Timezone หากไม่คุมที่ชั้นข้อมูล
- ภาระงานเจ้าหน้าที่ช่วงพีคอาจกระทบ SLA การอนุมัติ

## 15. แผนการทบทวนเอกสาร
